# 5. HS256 JWTs with pinned algorithm, issuer, and expiry

Status: Accepted

## Context

The challenge requires HMAC-SHA256 (`HS256`) tokens validated by middleware. JWT verification has well-known ways to go wrong: accepting `alg: none`, accepting an RS256 token whose "public key" is the HMAC secret, or skipping expiry entirely.

## Decision

Use `golang-jwt/jwt/v5` with a keyfunc that rejects any token whose signing method is not HMAC, and parse with `WithIssuer` and `WithExpirationRequired`. Claims are the registered set only: `sub` (the user ID), `iss`, `iat`, `exp`. Verification returns the subject, and the middleware puts it in the request context.

The secret comes from `JWT_SECRET` with no default ([ADR-0008](0008-mandatory-jwt-secret.md)).

## Consequences

Algorithm confusion and unsigned tokens are rejected structurally, not by convention. A token missing `exp` is refused rather than treated as eternal. Tests cover the expired, wrong-secret, wrong-issuer, garbage, and `alg: none` cases — the last one uses a hand-built token so it is a real test of the keyfunc.

Consequences of the shape chosen: tokens carry no roles or permissions, so any authorization decision needs a lookup or a separate rule ([ADR-0010](0010-self-only-writes.md)). They are also stateless, so there is no revocation — a leaked token is valid until `exp` (default 24h). A refresh-token flow with a short-lived access token is the usual answer and is out of scope here.

HS256 means every service that verifies a token can also mint one. That is fine for a single service; a multi-service deployment should move to RS256 so verifiers only hold a public key.
